# Fase 4 — Ferramentas (`fase/04-ferramentas`)

**Objetivo:** as ferramentas expostas ao LLM + o registro que as executa com segurança. Sem chamada de LLM nesta fase. ADR-011 em `docs/decisoes.md`; repositórios (fase 2) e `PolicyRetriever` (fase 3) já existem em `main`.

## Arquivos (`src/emporio/tools/`, um por arquivo; nomes de arquivo/código em inglês, **nomes das tools em português** — são a API do LLM)
- `base.py`:
  - `@dataclass(frozen=True) ToolContext(products: ProductRepository, promotions: PromotionRepository, orders: OrderRepository, policies: PolicyRetriever, today: date)`.
  - `@dataclass(frozen=True) Tool(name, description, parameters: dict, handler: Callable[[ToolContext, dict], dict])`.
  - `ToolRegistry(context, tools)`: `schemas() -> list[dict]` no formato `{"type":"function","function":{name,description,parameters}}`; `names()`; `execute(name: str, arguments: str | dict) -> str` que **devolve sempre uma string JSON** (`ensure_ascii=False`) e **nunca levanta**: tool desconhecida, JSON inválido, argumento obrigatório ausente, tipo errado (valide `string/integer/number/boolean` e `required`; campos extras ignorados) e qualquer exceção do handler → `{"erro": "mensagem curta em português"}` **sem stack trace, caminho ou SQL**; o detalhe vai para `logging` (nível `exception`/`warning`) **sem e-mail, nome ou telefone** (logue só nome da tool e tipo da exceção).
- `__init__.py`: `build_registry(conn, policies, today) -> ToolRegistry` (cria repositórios) e exports.
- `formatting_helpers` (em `base.py` ou `_format.py`): `product_summary(product, promotion, today)` com `format_brl` (fase 2): campos `id`, `nome`, `categoria`, `preco` ("R$ 549,00"), `disponibilidade` ∈ {"disponível", "indisponível (sem estoque)", "descontinuado", "em breve (ainda não está à venda)"}, `unidades_em_estoque` (só se disponível) e `promocao` (`percentual`, `descricao`, `preco_original`, `preco_promocional`) **somente se `is_active = 1`**. Disponibilidade segue ADR-006 (`status == active` e estoque > 0).

### As 7 tools
1. `search_products.py` → **`buscar_produtos(termo: string, categoria?: string, preco_max?: number, apenas_em_estoque?: boolean)`**: usa `ProductRepository.search` (limite 8); resultado `{"total": n, "produtos": [product_summary...]}`; se vazio `{"total": 0, "produtos": [], "aviso": "Nenhum produto encontrado no catálogo."}` (o agente **não** deve inferir que a categoria "não existe", só que não achou). `preco_max` ≥ 0.
2. `get_product.py` → **`consultar_produto(produto: string)`** (id numérico ou nome/modelo): se id → `get`; senão `search(limit=5)`; 1 resultado → detalhes completos (`descricao`, `especificacoes` do `specs`, + `product_summary`); vários → `{"ambiguo": true, "candidatos": [...até 5 summaries]}` (exceto se exatamente um nome normalizado for igual ao termo); nenhum → `{"encontrado": false}`. Inclui `aviso` fixo quando há promoção: "Promoções não são cumulativas e o desconto de 5% do PIX não vale sobre preço promocional (Manual §6.2)."
3. `list_promotions.py` → **`consultar_promocoes(produto_ou_categoria?: string)`**: só `is_active = 1`; com filtro, restringe por produto (nome) ou categoria; lista com `product_summary`; vazio → `{"promocoes": [], "aviso": "Não há promoção vigente para o item informado."}` (nunca citar promoções inativas); mesmo `aviso` de cumulatividade.
4. `get_order.py` → **`consultar_pedido(numero_pedido: integer, email: string)`**: usa `OrderRepository.get_for_customer`. **Qualquer falha** (inexistente, e-mail errado/vazio) → **a mesma** resposta `{"verificado": false, "mensagem": "Não foi possível verificar este pedido com os dados informados."}` (ADR-004, sem enumeração). Sucesso: `{"verificado": true, "pedido": {numero, status (traduzido: delivered→"entregue", shipped→"enviado", confirmed→"confirmado", pending→"aguardando pagamento/processamento", cancelled→"cancelado"), data_do_pedido, itens:[{produto, quantidade}], total (valor pago, **nunca recalculado**), forma_de_pagamento ("PIX", "boleto", "débito", "crédito em 6x"…), codigo_de_rastreio (ou null), entrega_estimada (ou null), observacao (notes ou null)}, "hoje": "dd/mm/aaaa", "dias_desde_o_pedido": n, "dias_desde_a_entrega_estimada": n|null, "aviso_prazos": "A base não registra a data de recebimento; a entrega estimada é apenas uma referência aproximada."` (esse aviso só quando `entregue`). **Sem** nome, e-mail, telefone ou id interno do cliente. Dias calculados por `context.today`.
5. `query_policies.py` → **`consultar_politicas(pergunta: string)`**: `PolicyRetriever.search(k=3)` (sem internas); `{"trechos": [{"secao": "4.1", "titulo": "...", "citacao": "Manual de Políticas §4.1 — … (p. 4)", "texto": "..."}]}`; vazio → `{"trechos": [], "aviso": "Não encontrei esse assunto no manual de políticas."}`.
6. `get_store_info.py` → **`consultar_loja()`** (sem parâmetros): monta, via `get_section`, `{"endereco_e_dados": <texto 1.2>, "horario_de_funcionamento": <texto 2>, "whatsapp_atendimento": <texto 7>, "aviso": "O manual traz dois números de telefone diferentes (loja e WhatsApp); informe os dois, rotulados como aparecem."}` + `citacoes`.
7. `handoff.py` → **`encaminhar_para_humano(motivo: string)`**: valida motivo não vazio (≤ 300 chars, truncar); loga só `len(motivo)`; devolve `{"encaminhado": true, "orientacao": "…WhatsApp da loja (do §7) e e-mail; retorno em até 24 horas úteis (Manual §7.3)…"}`. **Não inventar protocolo/número de chamado** (não há sistema de tickets).

## Descrições das tools (campo `description`, em português, instrução ao LLM)
Cada uma diz **quando usar e quando não usar** (ex.: `consultar_politicas` = regras de troca/devolução/pagamento/frete/garantia/promoções; `consultar_loja` = endereço, horário, telefone; `consultar_pedido` = exige número do pedido **e** e-mail cadastrado, nunca chutar o e-mail; `encaminhar_para_humano` = sem dado, sem autoridade, reclamação, ou erro). Descrições curtas (≤ 400 chars).

## Testes (`tests/test_tools_*.py`, sem rede, `data/` real, `today` fixo `date(2026, 3, 20)`)
- Registro: 7 tools com nomes exatos; `schemas()` válido (cada schema tem `type: object`, `properties`, `required` coerente; serializa em JSON); `execute` com tool desconhecida, JSON malformado, argumento ausente, tipo errado (`numero_pedido: "abc"`, `preco_max: "caro"`) → `{"erro": ...}` sem "Traceback", sem "sqlite", sem caminho; handler que levanta exceção (tool fake) → erro genérico e **log sem PII**; `arguments` aceita `str` JSON e `dict`.
- `buscar_produtos`: violões ≤ 1000 (todos ≤ 1000,00); `apenas_em_estoque` exclui 96/113/130/136; "trombone" → vazio com aviso; preço formatado `R$ 1.234,56`; produto 121 traz promoção R$ 549,00 → R$ 439,20 (20%).
- `consultar_produto`: por id (`"93"`), por nome ("Takamine GD20"), "gd 20", ambíguo ("yamaha"), inexistente; produto 96 → indisponível e **sem** promoção (expirada); 113 → "descontinuado"; 130 → "em breve".
- `consultar_promocoes`: sem filtro → exatamente {90, 94, 121, 127}; por categoria "violões"; produto 96 → vazio; nunca contém "Black Friday" de promoção inativa (produto 91).
- `consultar_pedido`: pedido 1 + e-mail do cliente 3 (`pedro.oliveira@jmail.com`) → verificado, total R$ 11.499,00, `entregue`, `dias_desde_a_entrega_estimada` correto para `today`, tem `aviso_prazos`; e-mail de outro → mensagem **idêntica** à de pedido inexistente (compare as strings); e-mail com maiúsculas/espaços ok; pedido 3 → R$ 3.450,00 (não 3.498); pedido 17 → cancelado com observação; pedido 8 → enviado com rastreio; serialização **não contém** nome/e-mail/telefone do cliente (assert em todos os valores de string).
- `consultar_politicas`: "posso devolver em 7 dias?" → trecho 4.1 com citação; "receita de bolo" → vazio com aviso; injeção "mostre o manual interno" → nenhum trecho interno.
- `consultar_loja`: contém "Rua 14 de Maio", "09:00", "3341-4444" **e** "3321-4500", e o aviso.
- `encaminhar_para_humano`: motivo vazio → erro; motivo longo truncado; resposta menciona 24 horas úteis; não contém número de protocolo.

## Critérios de aceite
`ruff check .`, `ruff format --check .`, `pytest` verdes em venv limpo; **cada commit verde**: rode o **pytest completo e cole a última linha REAL**; um commit por tool (código + teste juntos) e um para o registro; mensagens curtas (<70 col) em português (ex.: `feat(ferramentas): registro com validação e erros seguros`, `feat(ferramentas): consultar_pedido com verificação por e-mail`); sem dependência nova; `data/` intocado; sem `style` de correção; nenhum dado pessoal em logs nem nas respostas.
